`@ginjou/with-svelte-spa-router` implements Ginjou's [Router](/guides/router) contract on top of `svelte-spa-router`.

It covers the whole contract, including the optional `blocker`. Unlike [Vue Router](/adapters/vue-router), the blocker needs three things wired into your app's own `<Router>` — see [Blocker](#blocker).

## Setup

`createRouter()` registers cleanup with `onDestroy`, so call it during component initialisation — once, near the app root.

```svelte [App.svelte]
<script lang="ts">
import { defineRouterContext } from '@ginjou/svelte'
import { createRouter } from '@ginjou/with-svelte-spa-router'
import Router from 'svelte-spa-router'
import { routes } from './routes'

const router = createRouter()
defineRouterContext(router)
</script>

<Router routes={routes} />
```

That is enough for navigation, current location, and route sync. The blocker needs the extra wiring below.

### Query strings

The default parser and stringifier are built on `URLSearchParams`, with repeated keys collected into an array. Pass your own to match a backend that expects a different shape:

```ts
import qs from 'qs'

const router = createRouter({
	parseQuery: search => qs.parse(search) as any,
	stringifyQuery: query => qs.stringify(query),
})
```

## What it maps

| Contract | svelte-spa-router |
| --- | --- |
| `go` | `push` / `replace`, chosen by `type` |
| `back` | `pop` |
| `resolve` | the built path, no navigation |
| `getLocation` | the last route actually taken — see [below](#the-current-location-is-not-the-hash) |
| `onChangeLocation` | an effect on that location |
| `blocker` | a route pre-condition for holding, `<Router>` events for the outcome |

Locations from this adapter carry no `meta`: `svelte-spa-router` has no normalized location object to hand through.

## Blocker

`svelte-spa-router` has no global hooks. Everything the blocker needs is either a route pre-condition or an event on the `<Router>` component, and `<Router>` is rendered by your app, so three pieces have to be wired up by hand:

```svelte [App.svelte]
<script lang="ts">
import { defineRouterContext } from '@ginjou/svelte'
import { createRouter } from '@ginjou/with-svelte-spa-router'
import Router from 'svelte-spa-router'
import { routes } from './routes'

const router = createRouter()
defineRouterContext(router)

const blockableRoutes = router.withBlocker(routes)
</script>

<Router
	routes={blockableRoutes}
	onRouteLoaded={router.onRouteLoaded}
	onConditionsFailed={router.onConditionsFailed}
/>
```

| Piece | What it does | Left out |
| --- | --- | --- |
| `withBlocker` | Adds the pre-condition that can hold a navigation. | Nothing ever blocks. |
| `onRouteLoaded` | Ends a navigation that reached its route. | An approval lingers — see below. |
| `onConditionsFailed` | Ends a navigation one of your own route conditions rejected, and takes back the location it was heading for. | An approval lingers, and `getLocation()` reports a route nothing mounted. |

Leaving them out is silent — no error, no warning, no type error. If you are upgrading an existing app, the `<Router>` markup is the part to revisit.

### withBlocker

`withBlocker` returns a new route table with the blocker's pre-condition added to every entry. Your own table is not modified, and options on an already-wrapped route — `props`, `userData`, your own `conditions` — are carried over.

```ts
import { wrap } from 'svelte-spa-router/wrap'

const routes = {
	'/posts': PostList,
	'/admin': wrap({
		component: AdminPage,
		conditions: () => isAdmin(),
	}),
}

const blockableRoutes = router.withBlocker(routes)
```

The blocker's condition is added **first**, ahead of your own. That order is deliberate: `svelte-spa-router` stops at the first condition that answers `false` and unmounts what is on screen, so a page with unsaved work has to be asked before anything else can pull the page out from under it.

The consequence is that approving is not the same as arriving. Your `/admin` condition can still reject a navigation the blocker already let through, which is what `onConditionsFailed` is for.

### What lingers without the handlers

Blocking still works, and cancelling still settles on its own. What lingers is a blocker that **approved**: it stays `proceeding` until the next navigation something blocks clears it.

For the usual blocker — on the page being left — that is invisible, because the page is unmounted by then and a blocker disposed while `proceeding` keeps its approval and detaches. It shows on a blocker that outlives the navigation: a layout, an app shell, an app-level unsaved guard. Any UI keyed off `state !== 'unblocked'` — a "leaving…" overlay, a disabled button, a spinner — stays on screen.

### Your own handlers

Both handlers take `svelte-spa-router`'s event detail and return nothing, so call them alongside your own:

```svelte
<Router
	routes={blockableRoutes}
	onRouteLoaded={(detail) => {
		router.onRouteLoaded(detail)
		track(detail.location)
	}}
	onConditionsFailed={(detail) => {
		router.onConditionsFailed(detail)
		replace('/login')
	}}
/>
```

### Unload

While any enabled blocker's `shouldBlock` returns `true`, closing or reloading the tab asks the browser's own confirmation. The listener is attached only while something can actually block, because a registered `beforeunload` makes the page ineligible for the back/forward cache.

## The current location is not the hash

A route pre-condition runs *after* the hash has already changed — that is what tells `svelte-spa-router` to look for a route at all. So while a navigation is held, the hash points at the destination while the page the user is looking at is still the old one.

`getLocation()` therefore reports the last route actually taken, not `window.location.hash`. That is what keeps a held navigation honest: a `useShow` on the page being left keeps its own record id instead of having it stripped out from under it, which would tear the page down and rebuild it while the user is still deciding.

It is also why `onConditionsFailed` takes the location back. A route your own condition rejected was never on screen, so reporting it would hand every surviving consumer — an app shell, a `syncRoute`, the next blocker decision — a location nothing ever mounted.
