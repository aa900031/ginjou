`@ginjou/with-vue-router` implements Ginjou's [Router](/guides/router) contract on top of Vue Router.

It covers the whole contract, including the optional `blocker`, so `useRouteBlocker` and `useWarnUnsaved` work with nothing extra to wire up.

## Installation

---
sync: package-manager
---

```bash [pnpm]
pnpm add @ginjou/with-vue-router
```


```bash [npm]
npm install @ginjou/with-vue-router
```

```bash [bun]
bun add @ginjou/with-vue-router
```

Vue Router is a peer dependency. The package works with Vue 2.7 and Vue 3 through `vue-demi`.

## Setup

`createRouter()` reads the active Vue Router instance with `useRouter()` and subscribes to it, so call it inside `setup` — once, near the app root — and register the result as the router context.

```vue [App.vue]
<script setup lang="ts">
import { defineRouterContext } from '@ginjou/vue'
import { createRouter } from '@ginjou/with-vue-router'

defineRouterContext(createRouter())
</script>

<template>
	<RouterView />
</template>
```

Everything it subscribes to is torn down with the scope it was created in.

## What it maps

| Contract | Vue Router |
| --- | --- |
| `go` | `router.push` / `router.replace`, chosen by `type` |
| `back` | `router.back` |
| `resolve` | `router.resolve`, returning `href` |
| `getLocation` | `router.currentRoute` |
| `onChangeLocation` | a watcher on `router.currentRoute` |
| `blocker` | `router.beforeEach` for holding, `router.afterEach` and `router.onError` for the outcome |

### Route meta

`go` and `resolve` accept a `meta` of Vue Router's own options, so a named route with params is reachable through the contract:

```ts
router.go({
	type: 'push',
	meta: { name: 'post-edit', params: { id: 1 } },
})
```

Locations coming back out carry the normalized Vue Router location under `meta.location`:

```ts
const location = router.getLocation()
location.meta.location.matched // the matched route records
location.meta.location.name // the route name
```

That is the escape hatch for anything the contract's `path` / `params` / `query` / `hash` cannot express. The route blocker below is the main reason to reach for it.

## Blocker

Nothing to wire up: the adapter subscribes to `beforeEach` for holding a navigation and to both `afterEach` and `onError` for its outcome. Those cover every way a navigation ends — success, and every failure Vue Router reports as one (cancelled, aborted, duplicated) — while a guard or async component that throws only ever reaches `onError`.

### Which navigations reach shouldBlock

Every navigation Vue Router reports, with nothing filtered out on the way in. Whether a given one matters is the page's call, so `shouldBlock` gets both locations and decides.

Comparing paths is the obvious rule, and with Vue Router it is not enough. Three navigations where the path changes and only one of them takes the page away:

| Navigation | What Vue Router does | Hold it? |
| --- | --- | --- |
| `/posts/1/edit` → `/posts/2/edit` | Same record, so the component is reused — but everything derived from the id refetches and rehydrates the form. | Yes |
| `/posts/1/edit` → `/posts/1/edit/preview` | Enters a child. The form stays mounted and nothing is torn down. | No — it is a tab switch |
| `/posts/1` → `/p/1` (alias) | Same record and same params under a second path. Nothing is torn down. | No |

`meta.location` is what tells them apart, through two things a `RouterLocation` alone does not carry:

- **`matched`** — the record list Vue Router resolved. A navigation that only goes deeper still matches everything the current one does. Note that an alias resolves to its own record object, with the original under `aliasOf`, so records have to be compared through that.
- **`params`** — the records can stay while the record being *shown* changes, which is the first row.

```ts
import type { RouterBlockShouldInput } from '@ginjou/core'
import type { RouteParsedMeta } from '@ginjou/with-vue-router'
import type { RouteRecordNormalized } from 'vue-router'
import { useRouteBlocker } from '@ginjou/vue'

const origin = (record: RouteRecordNormalized): RouteRecordNormalized => record.aliasOf ?? record

function isLeavingRoute(
	{ currentLocation, nextLocation }: RouterBlockShouldInput<RouteParsedMeta>,
): boolean {
	// An unload has no next location to compare, and leaving the site loses the work either way.
	if (nextLocation == null)
		return true

	const current = currentLocation.meta.location
	const next = nextLocation.meta.location

	const nextRecords = next.matched.map(origin)
	const stays = current.matched.map(origin).every(record => nextRecords.includes(record))
	if (!stays)
		return true

	// Only the params this location already has: a child route introducing a new one is not a leave.
	return Object.keys(current.params).some(
		key => String(current.params[key]) !== String(next.params[key]),
	)
}

const blocker = useRouteBlocker({
	shouldBlock: input => isDirty.value && isLeavingRoute(input),
})
```

::note
[`useWarnUnsaved`](/guides/form#warn-about-unsaved-changes) uses `WarnUnsaved.isLeavingPath`, a plain path comparison. It gets the first row right and the other two wrong, so a form with nested tabs or an aliased record wants its own `useRouteBlocker` with a predicate like the one above rather than `warnUnsaved`.
::

### KeepAlive

A component cached by `<KeepAlive>` is deactivated, not unmounted, so its scope is never disposed and it cannot clean itself up on the way out. The adapter tracks that for you: a blocker registered inside a component is not asked while that component is deactivated, and is asked again once it is activated.

Without it a cached page would go on holding every later navigation with a confirmation rendered nowhere on screen.

This works because the adapter binds `onActivated` / `onDeactivated` at the moment `blocker` is called, which is why `useRouteBlocker` registers during `setup` rather than when `enabled` first turns true. A `blocker` created outside a component instance keeps working and simply has no activation state to track.

### Unload

While any enabled blocker's `shouldBlock` returns `true`, closing or reloading the tab asks the browser's own confirmation. The listener is attached only while something can actually block, because a registered `beforeunload` makes the page ineligible for the back/forward cache — an app that never blocks does not pay for it.

## Location sync

`onChangeLocation` is what [`syncRoute`](/guides/list#sync-with-route) and `useLocation` are built on, and it is muted from the moment the subscribing component's own route record starts being left.

Without that, the watcher — which runs before the component is torn down — would hand a list controller a location the page does not belong to, and it would write its filters into the wrong route's query on the way out.

The mute lifts on its own when the leave turns out not to have happened: a guard rejected the navigation, or a later navigation came back to the same path. A cached component starts reporting again when it is activated.
