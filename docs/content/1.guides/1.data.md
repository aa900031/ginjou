The data layer is where Ginjou reads and writes data.

This page focuses on fetchers, low-level composables, and the shared behaviors that sit underneath higher-level controllers.

```mermaid
flowchart LR
	A[Data Composable] --> B[TanStack Query]
	B --> C[Fetcher method]
	C --> D[Backend]
```

## Fetcher Context

Fetcher context is where the app registers one or more fetchers.

Those fetchers follow the shared fetcher contract, and every query or mutation composable eventually calls one fetcher method.

### Interface

::code-group

```ts [Fetcher]
interface Fetcher<TRecord = any> {
	getList?: (props: {
		resource: string
		pagination?: { current: any, perPage: number }
		sorters?: Array<{ field: string, order: 'asc' | 'desc' }>
		filters?: unknown[]
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord[], total: number }>

	getOne?: (props: {
		resource: string
		id: string | number
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord }>

	getMany?: (props: {
		resource: string
		ids: Array<string | number>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord[] }>

	createOne?: (props: {
		resource: string
		params: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord }>

	createMany?: (props: {
		resource: string
		params: Array<Record<string, any>>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord[] }>

	updateOne?: (props: {
		resource: string
		id: string | number
		params?: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord }>

	updateMany?: (props: {
		resource: string
		ids: Array<string | number>
		params?: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord[] }>

	deleteOne?: (props: {
		resource: string
		id: string | number
		params?: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord }>

	deleteMany?: (props: {
		resource: string
		ids: Array<string | number>
		params?: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord[] }>

	custom?: (props: {
		url: string
		method: 'get' | 'post' | 'put' | 'patch' | 'delete' | 'head' | 'options'
		query?: Record<string, any>
		payload?: Record<string, any>
		headers?: Record<string, any>
		meta?: Record<string, any>
	}) => Promise<{ data: TRecord }>
}
```

::

Custom requests can also carry `filters`, `sorters`, `query`, `headers`, and `payload`.

The exact translation is fetcher-specific. Use this shape when the endpoint is not a standard resource action but should still share Ginjou query keys, notifications, auth error handling, and realtime options.

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useCustom } from '@ginjou/vue'
import { computed } from 'vue'

const searchQuery = useCustom({
	url: '/search/posts',
	method: 'get',
	filters: [
		{ field: 'status', operator: 'eq', value: 'published' },
	],
	sorters: [
		{ field: 'createdAt', order: 'desc' },
	],
	query: {
		q: keyword.value,
	},
	headers: {
		'X-Feature': 'advanced-search',
	},
})

const results = computed(() => searchQuery.record.value?.items ?? [])
```

```ts [Svelte]
import { useCustom } from '@ginjou/svelte'

const searchQuery = useCustom(() => ({
	url: '/search/posts',
	method: 'get',
	filters: [
		{ field: 'status', operator: 'eq', value: 'published' },
	],
	sorters: [
		{ field: 'createdAt', order: 'desc' },
	],
	query: {
		q: keyword,
	},
	headers: {
		'X-Feature': 'advanced-search',
	},
}))

const results = $derived(searchQuery.record?.items ?? [])
```

### Methods

| Method | Explanation | Composables |
| --- | --- | --- |
| getList | Read a collection | `useGetList`, `useGetInfiniteList` |
| getOne | Read one record | `useGetOne`, `useGetManyByOne` |
| getMany | Read many records by ids | `useGetMany` |
| createOne | Create one record | `useCreateOne` |
| createMany | Create many records | `useCreateMany` |
| updateOne | Update one record | `useUpdateOne` |
| updateMany | Update many records | `useUpdateMany` |
| deleteOne | Delete one record | `useDeleteOne` |
| deleteMany | Delete many records | `useDeleteMany` |
| custom | Handle non-CRUD read or write | `useCustom`, `useCustomMutation` |

Adapter support varies. Some backend packages implement only a subset of these methods.

You do not need to implement every method on day one.

Start with the methods your app really uses, then add more as pages need them.

::code-group
---
sync: guide-example
---

```ts [Vue]
import { defineFetchersContext } from '@ginjou/vue'

defineFetchersContext({
	default: {
		async getList({ resource }) {
			const response = await fetch(`/api/${resource}`)
			const data = await response.json()

			return {
				data,
				total: data.length,
			}
		},
		async getOne({ resource, id }) {
			const response = await fetch(`/api/${resource}/${id}`)

			return {
				data: await response.json(),
			}
		},
		async createOne({ resource, params }) {
			const response = await fetch(`/api/${resource}`, {
				method: 'POST',
				headers: { 'Content-Type': 'application/json' },
				body: JSON.stringify(params),
			})

			return {
				data: await response.json(),
			}
		},
		async updateOne({ resource, id, params }) {
			const response = await fetch(`/api/${resource}/${id}`, {
				method: 'PUT',
				headers: { 'Content-Type': 'application/json' },
				body: JSON.stringify(params),
			})

			return {
				data: await response.json(),
			}
		},
		async deleteOne({ resource, id }) {
			const response = await fetch(`/api/${resource}/${id}`, {
				method: 'DELETE',
			})

			return {
				data: await response.json(),
			}
		},
	},
})
```

## Resource

`resource` names the record set.

`fetcherName` picks the data source.

Most calls only need `resource`. Add `fetcherName` when more than one backend is registered and a request should target a specific one.

::code-group
---

---

```ts [Vue]
import { useGetList, useGetOne, useUpdateOne } from '@ginjou/vue'

const postsList = useGetList({
	resource: 'posts',
})

const postDetail = useGetOne({
	resource: 'posts',
	id: 1,
})

const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
})
```

### `filters`

Filters are a tree.

Use one rule for simple cases. Use `and` or `or` when the backend query needs grouped conditions.

Conditional Operator:

| Operator | Explanation |
| --- | --- |
| `and` | All child filters must match. |
| `or` | Any child filter can match. |

Logical Operator

| Operator | Explanation |
| --- | --- |
| `eq` | Equal to the value. |
| `ne` | Not equal to the value. |
| `lt` | Less than the value. |
| `gt` | Greater than the value. |
| `lte` | Less than or equal to the value. |
| `gte` | Greater than or equal to the value. |
| `in` | Match a value in a list. |
| `nin` | Exclude a value in a list. |
| `contains` | Text contains the value. |
| `ncontains` | Text does not contain the value. |
| `containss` | Case-sensitive contains. |
| `ncontainss` | Case-sensitive not contains. |
| `startswith` | Text starts with the value. |
| `nstartswith` | Text does not start with the value. |
| `startswiths` | Case-sensitive starts with. |
| `nstartswiths` | Case-sensitive not starts with. |
| `endswith` | Text ends with the value. |
| `nendswith` | Text does not end with the value. |
| `endswiths` | Case-sensitive ends with. |
| `nendswiths` | Case-sensitive not ends with. |
| `between` | Match a range. |
| `nbetween` | Exclude a range. |
| `null` | Value is null. |
| `nnull` | Value is not null. |

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useGetList } from '@ginjou/vue'

const postsQuery = useGetList({
	resource: 'posts',
	filters: [
		{ field: 'status', operator: 'eq', value: 'published' },
		{
			operator: 'or',
			value: [
				{ field: 'title', operator: 'contains', value: keyword.value },
				{ field: 'summary', operator: 'contains', value: keyword.value },
			],
		},
	],
})
```

```ts [Svelte]
import { useGetList } from '@ginjou/svelte'

const postsQuery = useGetList(() => ({
	resource: 'posts',
	filters: [
		{ field: 'status', operator: 'eq', value: 'published' },
		{
			operator: 'or',
			value: [
				{ field: 'title', operator: 'contains', value: keyword },
				{ field: 'summary', operator: 'contains', value: keyword },
			],
		},
	],
}))
```

`useGetOne` reads one record.

## Get Many

`useGetMany` reads many records from known ids.

If `fetcher.getMany` is missing, Ginjou falls back to repeated `fetcher.getOne`. Records whose `getOne` fails with a 404 (`status`, `statusCode`, or `response.status`) are left out of the result, matching a `getMany` that returns only existing records; any other error fails the query.

It returns a TanStack `useQuery` result.

| Extra | Meaning |
| --- | --- |
| `records` | Shortcut for the returned records. |

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useGetMany, useGetOne } from '@ginjou/vue'
import { computed } from 'vue'

const postQuery = useGetOne({
	resource: 'posts',
	id: 1,
})

const commentsQuery = useGetMany({
	resource: 'comments',
	ids: computed(() => postQuery.record.value?.commentIds ?? []),
})

const comments = computed(() => commentsQuery.records.value ?? [])
```

```ts [Svelte]
import { useGetMany, useGetOne } from '@ginjou/svelte'

const postQuery = useGetOne({
	resource: 'posts',
	id: 1,
})

const commentsQuery = useGetMany(() => ({
	resource: 'comments',
	ids: postQuery.record?.commentIds ?? [],
}))

const comments = $derived(commentsQuery.records ?? [])
```

::

## Get Many by One

`useGetManyByOne` reads many records from known ids.

It runs one `getOne` query for each id and combines those results into one TanStack `useQuery` result.

Use it when the same related record can appear in multiple places, such as users shared across posts, and existing `getOne` cache entries can be reused. Unlike `useGetMany`, it does not call `fetcher.getMany`.

`queryOptions` can also be a function. Ginjou calls it for each id with `{ id, index }` and uses the returned value as that record's `getOne` query options.

| Extra | Meaning |
| --- | --- |
| `records` | Shortcut for the returned records. |

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useGetList, useGetManyByOne } from '@ginjou/vue'
import { computed } from 'vue'

const postsQuery = useGetList<{
	id: string
	title: string
	userId: string
}>({
	resource: 'posts',
})

const userIds = computed(() =>
	Array.from(
		new Set((postsQuery.records.value ?? []).map(post => post.userId)),
	),
)

const usersQuery = useGetManyByOne<{
	id: string
	name: string
}>({
	resource: 'users',
	ids: userIds,
	queryOptions: ({ index }) => ({
		staleTime: index === 0 ? 60_000 : 5_000,
	}),
})

const users = computed(() => usersQuery.records.value ?? [])
```

```ts [Svelte]
import { useGetList, useGetManyByOne } from '@ginjou/svelte'

const postsQuery = useGetList<{
	id: string
	title: string
	userId: string
}>({
	resource: 'posts',
})

const userIds = $derived(
	Array.from(
		new Set((postsQuery.records ?? []).map(post => post.userId)),
	),
)

const usersQuery = useGetManyByOne<{
	id: string
	name: string
}>(() => ({
	resource: 'users',
	ids: userIds,
	queryOptions: ({ index }) => ({
		staleTime: index === 0 ? 60_000 : 5_000,
	}),
}))

const users = $derived(usersQuery.records ?? [])
```

## Mutation Mode

`mutationMode` controls when update and delete feel committed.

Choose it based on the UX promise of the page, not just on backend speed.

| Mode | Meaning | Composables |
| --- | --- | --- |
| pessimistic | wait for the server | `useUpdateOne`, `useUpdateMany`, `useDeleteOne`, `useDeleteMany` |
| optimistic | update cache first | `useUpdateOne`, `useUpdateMany`, `useDeleteOne`, `useDeleteMany` |
| undoable | wait for a timeout before the real request | `useUpdateOne`, `useUpdateMany`, `useDeleteOne`, `useDeleteMany` |

### `pessimistic`

Use this when the UI should only change after the server confirms success.

::code-group
---

### `optimisticUpdate`

In `optimistic` and `undoable` modes, Ginjou updates cached `list`, `many`, and `one` queries before the server response settles.

Use `optimisticUpdate` when you need to skip or customize those cache updates.

| Value | Meaning |
| --- | --- |
| `true` or omitted | Use Ginjou's default cache updater. |
| `false` | Skip that cache group. |
| function | Return the next cached query data yourself. |

Update functions receive `(previous, params, target)`. For `list` and `many`, `target` is the `id` or `ids` passed to the mutation. For `one`, `target` is always a single id.

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useUpdateOne } from '@ginjou/vue'

const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
	mutationMode: 'optimistic',
	optimisticUpdate: {
		list: false,
		many: true,
		one(previous, params, id) {
			if (!previous)
				return

			return {
				...previous,
				data: {
					...previous.data,
					...params,
					id,
					previewTitle: params.title,
				},
			}
		},
	},
})
```

```ts [Svelte]
import { useUpdateOne } from '@ginjou/svelte'

	resource: 'posts',
	id: 1,
	mutationMode: 'optimistic',
	optimisticUpdate: {

			return {
				...previous,
				data: {

					id,

				},
```

## Cache Invalidation

`invalidates` controls which cached queries should refresh after a mutation. Create mutations invalidate only after success; update and delete mutations invalidate once they settle, after success **or** failure.

Targets are `all`, `resource`, `list`, `many`, and `one`. `all` invalidates every query of a single fetcher, not every fetcher.

`'one'` and `'many'` work on the affected IDs passed as `ids` in the invalidate context. Mutations pass them for you: the mutation's `id` / `ids` plus every ID in the result. `'one'` refreshes every one query of those IDs, and `'many'` refreshes every many query whose `ids` include one of them, whatever `meta` the queries were fetched with. Without `ids` the rule is skipped with a `console.warn`; outside a mutation pass them yourself, as in `invalidate({ resource: 'posts', invalidates: ['one'] }, { ids: [1] })`.

Default invalidates:

| Composable | Default invalidates | Runs |
| --- | --- | --- |
| `useCreateOne` | list | on success |
| `useCreateMany` | list | on success |
| `useUpdateOne` | list, many, one | on settled |
| `useUpdateMany` | list, many, one | on settled |
| `useDeleteOne` | list, many | on settled |
| `useDeleteMany` | list, many | on settled |

Create mutations skip `'many'` by default: a new record's ID can't be in a many query fetched before it existed. If your app requests an ID before creating it (for example a client-generated UUID), add it back with `invalidates: ['list', 'many']`.

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useUpdateOne } from '@ginjou/vue'

const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
	invalidates: ['one', 'list'],
})
```

```ts [Svelte]
import { useUpdateOne } from '@ginjou/svelte'

const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
	invalidates: ['one', 'list'],
})
```

::

Passing `invalidates` replaces the defaults, so list the defaults you still want next to the extra rules:

```ts
const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
	invalidates: [
		'list',
		'many',
		'one',
		{ target: 'resource', resource: 'comments' },
		{ target: 'one', resource: 'authors', id: 1 },
		{ target: 'all', fetcherName: 'legacy' },
	],
})
```

`invalidates` can also be a callback. It receives the invalidate context `{ ids, data }`: `ids` the affected IDs and `data` the mutation result. It does not receive the defaults or the mutation props; to invalidate based on the variables you passed to `mutate`, create the invalidator with `useQueryInvalidate()` during setup and call it from that call's `onSuccess`, as in `mutate(vars, { onSuccess: () => invalidate({ resource: 'authors', invalidates: [{ target: 'one', id: vars.params.authorId }] }) })`. Use `data` to target related records the server returned, such as a comment's parent post:

```ts
const createComment = useCreateOne({
	resource: 'comments',
	invalidates: ({ data }) => [
		'list',
		...(data?.data.postId != null ? [{ target: 'one' as const, resource: 'posts', id: data.data.postId }] : []),
	],
})
```

For update and delete mutations the callback also runs when the mutation fails, with `data` set to `undefined`, so guard it as above. Create mutations never call it on failure. Every rule must be valid: Ginjou checks all rules before invalidating anything, so one invalid rule (for example `{ target: 'one', id: undefined }`) cancels the whole invalidation, including `'list'`. Only add a rule once its ID is known, as the example does. An error thrown while invalidating (for example from the callback) does not fail the mutation; it is logged with `console.error` and that invalidation is skipped.

To tune how TanStack Query refetches, pass an object with `rules` plus `filters` and `options`. Each one replaces its default (`{ type: 'all', refetchType: 'active' }` and `{ cancelRefetch: false }`) entirely, so include any default fields you still want. A callback can return this form too:

```ts
const updatePost = useUpdateOne({
	resource: 'posts',
	id: 1,
	invalidates: {
		rules: ['list', 'one'],
		filters: { refetchType: 'all' },
		options: { cancelRefetch: true },
	},
})
```

Object rules use the mutation's `fetcherName` when omitted. Without `meta` they match queries of any `meta`; with `meta` they match only that exact `meta`. `filters` is spread over each rule's own filters, so its fields win for every rule: a `predicate` replaces the ID and `meta` matching of `'one'` rules, string `'many'` rules, and object `'many'` rules without `meta` (an object `'many'` rule with `meta` matches its exact key, so a `predicate` only narrows it further), and `exact: true` turns the key-prefix match of every rule into an exact match, which usually matches nothing. Only set them when you mean to override the rule's own matching. Use `useQueryInvalidate` outside a mutation:

```ts
import { useQueryInvalidate } from '@ginjou/vue' // or @ginjou/svelte

const invalidate = useQueryInvalidate()

await invalidate({
	invalidates: [{
		target: 'resource',
		resource: 'comments',
	}],
})
```

## Notifications

Query and mutation composables can show default success and error messages.

Use `successNotify` or `errorNotify` to replace them. Use `false` to disable them.

## Realtime

When realtime is enabled, query composables subscribe and standard mutation composables publish.

The default channel is `resources/{resource}`. `useCustom` and `useCustomMutation` can use their own channel or event.

## Meta

`meta` is the backend-specific extension point.

Ginjou forwards it to the fetcher and includes it in query keys. Use it for backend details that do not belong in the shared contract. Keep it small, and read the backend guides for the exact shape.

For example, the REST adapter forwards `meta.method` and `meta.headers` to standard resource requests.

::code-group
---
sync: guide-example
---

```ts [Vue]
import { useGetList } from '@ginjou/vue'

const postsQuery = useGetList({
	resource: 'posts',
	meta: {
		method: 'POST',
		headers: {
			'X-Tenant': 'team-a',
		},
	},
})
```

```ts [Svelte]
import { useGetList } from '@ginjou/svelte'

const postsQuery = useGetList({
	resource: 'posts',
	meta: {
		method: 'POST',
		headers: {
			'X-Tenant': 'team-a',
		},
	},
})
```
